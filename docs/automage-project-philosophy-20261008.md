# AutoMage 项目哲学

> **已冻结**的上游哲学文档（2026-10-08，owner 签署）。此后不再扩展理论，只做纠错。
>
> 这份文档只回答一个问题：**我们为什么相信 AutoMage 这种产品应该存在。** 它说明：
> - 问题从哪里来；
> - 技术条件改变了什么；
> - 产品选择了什么机制；
> - 人和 AI 的分工怎样重新划分。
>
> 它**不规定**任何页面、视觉或组件的形式。产品、官网、Console、销售叙事都可以引用它。
>

>
> 用词：工作、职责范围、问责、授权、依据在全文只有一个意思，见 §7。其中"职责范围"（AutoMage 承担的那部分）和"问责"（始终属于组织）不能混用。

## 0. 一段话

企业软件已经把业务对象记录下来，也自动化了能预先定义的流程。但真实的工作往往不能被预定义的流程完全穷尽；剩下的部分，在工作存在期间仍然要有人承担它的认知状态：记住目标和上下文，判断信息够不够，解释变化，追下一步，确保事情没有掉下去。负责人感受到的，是看不清、推不动、事后说不清。

大模型显著扩大了软件能承担的这类认知劳动的范围，但它也会出错。AutoMage 要把一次性的 AI 能力，变成组织里持续存在、受治理的工作能力：
- 承接一项工作中组织委托给它的职责范围，维持上下文；
- 带着依据和未知，在授权范围内推进；
- 到了边界，把正确的问题和足够的依据带给正确的人。

分工是这样的：
- 组织定义为什么做、愿意承担什么、谁来决定，并始终承担问责；
- 事实锚定在可追溯的现实来源上；
- AutoMage 承担认知、行动和连续性，让工作继续往前。

它的目标不是让组织多一个 AI 界面，而是让组织少一些必须靠人亲自维持才能继续运转的工作。

## 1. 起点：管理闭环断了

负责人每天碰到的问题很具体：

- "这件事为什么没人跟我说？"
- "上周不是定了吗，怎么还没做？"
- "现在到底卡在哪？"
- "为什么每次都要我自己去问？"

归成三句话：**看不清、推不动、事后说不清。**

这也是 AutoMage 的历史起点（据 owner 回顾，以及 2026-09-04 的讨论记录）：
- 最初的诉求，是减少较大组织里的管理资源浪费；
- 核心场景是：日报汇总，减少老板与员工之间的反复询问，提前发现项目风险，主动形成计划，追踪计划是否真正落实；
- 当时出现过"老板的第二大脑"这类管理视角的说法；
- 8 月用供应链把问题具体化，之后在仓库、采购、财务、销售的反复确认里，抽出了"协调税"：同步 → 汇报 → 追问 → 转述 → 汇总 → 催办 → 确认 → 再同步；
- 再后来意识到，"协调"这个词仍然太窄（见 §2）。

这些场景不是五个零散功能，而是同一个管理循环：

```text
看见 → 理解 → 决定 → 落实 → 再看见
```

它是组织的一种能力循环，**不是**一条固定的产品流程，也不对应任何固定的节点序列。

## 2. 机制：流程穷尽不了的部分，要有人承担它的认知状态

看不清和推不动，是同一个问题的两个表面：

- **可见性**：负责人不知道真实发生了什么；
- **连续性**：知道了以后，也没有东西保证事情一直走到结果。

ERP 管订单，CRM 管客户，WMS 管库存，IM 承载沟通，文档保存知识。每套系统都记下了自己那部分现实，而且大多高度可配置（AutoMage 不以"传统软件僵化"立论）。能预先定义的部分，现有系统已经做得很好。但真实的工作往往不能被预定义的流程完全穷尽：总有一部分，要等事情发生了才能理解和判断。

"发生了一件事"之后，下面这一串仍然要靠人推下去：

```text
知道发生了什么 → 知道还缺什么 → 知道下一步 → 知道谁有权做 → 真的去做 → 知道后来怎样
```

两个表面背后是同一个机制：**流程穷尽不了的那部分，在工作存在期间需要某个主体承担它的认知状态。** 承担它，意味着要做到这几件事：
- 记住目标和上下文；
- 解释新的信息和变化；
- 判断下一步；
- 知道什么时候算结束；
- 确保它没有掉下去。

人在这里，实际上是组织的认知中间件。

这不只是协调。独立研究、专业分析、持续监测、内容生产、工具操作也一样。它们未必牵涉很多人，也未必持续很久，有的两分钟，有的半年；但在存在期间，都需要有人承担它的认知状态。

这份承担最昂贵的代价，是人的持续注意力：一件事要靠某个人一直记着、一直盯着，才不会掉下去。企业缺的往往不是更多数据，而是**有人持续理解这些数据对眼前这件事意味着什么。**

## 3. 技术条件变了：能理解模糊的世界，也会理解错

专家系统、机器学习、OCR、自然语言处理、RPA，都曾让软件承担过一部分认知工作。但每遇到一种新情况，往往要工程师事先写好规则，或者专门训练一个模型。

大模型和 Agent 显著扩大了软件能承担的非结构化认知劳动的范围，也大幅降低了对每个例外事先编码的要求：很多例外现在可以在运行时理解。它们能够：
- 读懂自然语言，理解含糊的要求；
- 跨来源拼上下文，判断信息够不够；
- 主动追问未知；
- 按情况选择要用的能力；
- 随现实变化重新计划；
- 用自然语言和不同角色沟通；
- 在规则之内决定下一步。

但它不是确定性系统。

> **AI 能理解模糊的世界，所以它有价值；AI 也会理解错模糊的世界，所以它必须带着证据和边界工作。**

所以依据、来源、显式的未知、授权边界、审计、重新打开，都不是为了合规后来套上的外壳，而是从模型能力本身推出来的结构。没有它们，这种能力进不了组织。

## 4. AutoMage 的选择

> **把一次性的 AI 能力，变成企业里持续存在、受治理的工作能力。**

### 4.1 它承接一项工作，以及组织委托给它的职责范围

AutoMage 承接的对象是**工作**，不是一次按钮操作，也不是一个孤立的任务。工作有两种形态，都属于核心模型：

| | 有限工作（finite work） | 持续职责（standing work） |
|---|---|---|
| 例子 | 处理一次缺料；完成一次供应商选择或行业研究；处理一项客户投诉 | 每天整理经营信息；持续监测库存或项目风险；定期检查客户续费风险 |
| 结构 | 开始、目标、进展、结果；可以关闭，也可以重新打开 | 目的、范围、节奏或触发条件、观察、介入条件、升级边界、每一周期的结果 |
| 结束 | 达到结果时关闭；前提变化时可以重新打开 | 没有天然的终点，只有暂停、撤销或调整范围 |

产品代码里已有的那条链（日报 → 汇总 → 决策选项 → 任务）就是一项持续职责：它每天运行，没有"完成"的一天。

在一项工作上，组织委托给 AutoMage 的是一段**职责范围**：哪些认知、行动和跟进由它承担。对这项工作的**问责**，仍然属于组织中的角色。

### 4.2 它维持什么

围绕一项工作，AutoMage 持续维持这些东西：
- 目的、上下文；
- 依据、未知；
- 可用能力、授权；
- 它的职责范围，以及问责属于谁；
- 当前状态、结果。

它的行为分三种情况：
- 世界变了：吸收新的事实，更新判断；
- 在授权范围内：自己推进；
- 到了边界：把正确的问题和足够的依据，带给正确的人。

### 4.3 它在哪里

AutoMage 是组织里的一层，不是一个新去处。它不替代 ERP、CRM、IM，也不要求人每天打开一个新的 AI 软件。各个部分的位置：

- **现有 IM**：人说话、确认、被召回的地方；
- **业务系统**：继续记录企业的业务对象，是重要的事实来源之一（不是唯一的来源，也可能过期或出错）；
- **Console**：组织在这里定义规则、授权和能力（方向）；
- **Runtime**：连接承载现实的系统，并在其中执行（方向）；
- **Skill**：工作需要时调用的能力载体。

聊天机器人把 AI 变成一个新的去处。AutoMage 要成为围绕工作持续运行的认知与行动层。

## 5. 分工怎样重新划分

组织里有四样东西需要分配：

- **目的**：为什么做；
- **认知**：怎么理解当前的情况；
- **行动**：下一步实际做什么；
- **问责与授权**：谁可以承诺什么，谁对结果负责。

AI 可以越来越多地承担中间两样；目的和问责仍然来自组织。

三方各自提供的东西：

```text
组织（人）           → 目的、问责、授权
可追溯的现实来源     → 依据
AutoMage             → 认知、行动、连续性
```

- **组织**：定义为什么做、愿意承担什么风险、哪些决定属于谁，并对结果负责。
- **现实来源**：约束什么可以被当作事实。
  - 业务系统、人、IM 消息、外部数据、文件、传感器，都可以是事实的来源。
  - 系统也可能过期或出错，所以事实要锚定在可追溯的来源上，来源之间冲突时要标出来。
  - AI 不能把自己的推断冒充成事实。
- **AutoMage**：承担被委托的认知、行动和跟进，让工作在两者之间持续向前。

由此推出四条原则：

1. **委托转移的是工作中认知和执行的承担，不自动转移最终的问责。** AutoMage 在授权内做的事，问责仍在组织。所以可追溯的记录不只是一份资产，而是让问责落得住的机制。
2. **边界由组织定义，而且不止一条。** 交代什么、给它什么、能做到哪、何时回来、什么算结束，都由组织决定。边界可以随工作类型、金额、风险、部门、数据和环境而不同。
3. **权限不会因为记录积累而自动扩大。** 记录为组织判断"保持、收紧还是扩大它的自主范围"提供依据；扩不扩大，始终是组织的决定。
4. **不是"AI 做小事、人做大事"，也不是"AI 最终替掉人"。** 长期模型也不是固定的"AI 建议、人拍板"。哪些动作它自己做、哪些需要确认、哪些必须由特定角色完成，本身是组织的配置。

## 6. 从例外管理理解它和人的关系

例外管理（management by exception）是理解"人的注意力什么时候应该进入"的一个视角，不是整个产品的定义。研究、内容生产、一次性分析，就未必以例外为中心。

管理学里的例外管理是说：管理者不必持续介入正常运行的事项，而应把注意力放在异常、偏差和需要判断的地方。

AutoMage 把它往前推了一步：
- 正常情况，由 AI 持续维持；
- 出现例外时才把人召回来：依据不足、风险变化、碰到授权边界、需要重大判断或新的信息。

这是运行原则和方向；今天的代码只实现了其中一部分（见 §9）。

对负责人来说，这是三种状态：

- **推（Push）**：不需要你的时候，不打扰你；
- **拉（Pull）**：你想看的时候，随时看得清组织的真实状态；
- **例外（Exception）**：真正需要你的时候，它主动带着依据来。

> **不需要人时不打扰；想看时能看清；需要人时带着依据来。**

这三种状态把三件事放到了一起：负责人的可见性、人的注意力成本、受治理的 AI 自主性。

2026-09-04 的讨论里有一句："日常尽量不可见，需要判断时及时出现，涉及权限时明确出现。"它是这三种状态在交互上的结果，不是一种 UI 风格。

所以，注意力是组织需要保护的资源。

> **AutoMage 的目标不是让组织多一个 AI 界面，而是让组织少一些必须靠人亲自维持才能继续运转的工作。**

## 7. 概念之间的关系

历史上，我们的抽象经历了：事件 → 工作的连续性 → 委托 → 职责范围。那是思考的演化，**不是**这些概念之间的上下级关系，后来的概念也不是前面概念的"高级版本"。

在当前模型里，它们是同一个工作系统的不同维度：

```text
事件 ──改变或触发──→ 工作（有限工作 / 持续职责）
                          │
                委托：组织与 AutoMage 关于这项工作的约定
                （职责范围、能力、授权、目标、何时回来找人、什么算结束）
                          │
                        行动 ──→ 结果

依据与未知：贯穿每一次判断
记录：留下全过程
问责：始终属于组织中的角色
```

| 概念 | 含义 |
|---|---|
| 事件 Event | 世界怎样改变。它改变或触发工作，本身不是持续存在的那个东西 |
| 工作 Work | AutoMage 承接的对象：有限工作或持续职责 |
| 委托 Delegation | 组织与 AutoMage 之间关于一项工作的约定。对内是一个配置对象；对企业负责人，是理解 AutoMage 最好的桥 |
| 职责范围 Responsibility scope | 一项工作中由 AutoMage 承担的认知、行动和跟进 |
| 问责 Accountability | 谁对结果和承诺负责。始终属于组织中的角色，不因委托而转移 |
| 能力 Capability | 它可以调用什么 |
| 授权 Authority | 它可以做到哪里。由组织决定 |
| 依据 Evidence（含未知 Unknown） | 判断所锚定的可追溯来源，以及还不知道什么 |
| 结果 Outcome | 有限工作何时真正结束；持续职责每一周期的结果 |
| 记录 Record | 过程留下的可追溯记录。是资产，不是产品身份 |

## 8. 我们不以这些定义 AutoMage

下面的"不是 X"都指**不以 X 定义产品边界**，不等于"产品中不得存在 X"。我们曾因为"六节点环不是本体"，把它的视觉和动效资产也一起删掉了；这是要避免的误读。

- 不能被还原成聊天机器人，也不是一个要人每天打开的新去处。对话仍然是重要的交互界面。
- 不只是"可以交代的 AI"。"给 AI 一个任务"，今天几乎所有 Agent 公司都能说。AutoMage 的特殊之处在于，这段委托：
  - 持续存在；
  - 连接现实来源；
  - 调用能力；
  - 受企业治理；
  - 随现实变化继续。
- 不以固定工作流或 RPA 定义产品边界；必要时可以把它们当作执行机制来调用。也不以"传统软件僵化"立论。
- 不以看板定义自己，也不以记录定义自己（Record 不是产品身份）。
- 不以"协调"为核心：协调只是最适合演示的一类。
- 不是供应链软件：供应链是有真实企业背景的参照场景。
- 它的权限不会自我扩张。

## 9. 今天的证据与方向

三类证据分开写，对应 handoff §1.5 的三层证据分级：

| 层次 | 内容 |
|---|---|
| **仓库中可验证的实现证据** | 产品仓库 `/root/neko/AutoMage/客制化` 的代码里有一条纵向切片：在飞书里收集团队日报，生成带来源的汇总，给出 A/B 决策选项，记录决定后生成任务并分派到人。另有员工、管理者、高管三级角色与权限，以及来源链接、决策记录、审计日志 |
| **有真实业务依据的场景** | 供应链缺料等场景：基于真实企业情况重构，数据与过程为演示 |
| **产品方向** | 直接读取和操作 WMS、ERP 等业务系统；日报之外的持续监测类职责；按动作配置的自主程度；Console 与 Runtime 的分工；正常情况由 AI 持续维持的运行方式 |

第一层描述的是代码层面可以验证的机制。代码存在，不等于已经形成客户可以直接使用的完整功能，也不证明已在客户的生产环境中运行。对外能否说"已经能用"，需要单独的产品或运行证据；在那之前，页面上不写"已经能用"，按 handoff §1.5 的要求保守措辞。

这些代码证据的价值在于：它们说明这套哲学不是今天才编出来的。

## 10. 对外表达的原则

- 从客户已经感受到的问题说起，再引入内部抽象；不从理论开场。
- 用业务语言表达，不要求客户先学会 Agent、Runtime、编排这类概念。
- "委托"是帮助企业负责人理解 AutoMage 的桥，不是产品的完整定义。

## 11. 仍在讨论

- "想看时能看清"在产品里以什么形态交付：定期汇总、随时询问，或两者都有。
- 例外的条件由谁、在哪里、以什么粒度配置。
- 组织调整授权边界时，需要看到什么样的记录才算足够。

已关闭（2026-10-08）：内部主对象叫"工作"（Work），有限工作和持续职责是它的两种形态；"职责范围"是工作上委托给 AutoMage 的那部分；"问责"始终属于组织。
