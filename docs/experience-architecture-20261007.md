# Experience Architecture · 2026-10-07

状态（2026-10-07 收档）：保留为设计推演记录。与 `docs/automage-website-implementation-handoff-20261007.md` 冲突之处，**一律以 implementation handoff 为准**（handoff 中修正了本文件的若干表述：semantic model 不得自动升格为全站契约、组件复用让位于新体验结构、拆开透镜采用三层语义、验证不使用简单比例门槛）。

## 0. 本轮输入假设（前几轮已定，不再论证）

- 认知主线：认问题 → 懂委托 → 跟完一件事 → 拆开 → 改规矩/换事情 → 认领。
- Homepage 承担前两拍，Supply Chain 承担中两拍，Capability 承担后两拍。
- 可配置物 = AI 在一件工作上的责任范围与自主程度。AutoMage 承接并持续推进工作；Record 是过程留下的持久表示，不是工作"变成"的目标。
- 产品仓库只是已证明的 vertical slice，不定义边界。

## 1. 三个页面各自的核心体验机制

同质化的真正来源不是视觉相似，而是三页姿态相同——都在"向访客解释"。修正方式是三种不同的体验姿态，共享同一套对象本体：

| 页面 | 机制 | 访客姿态 | 一句话 |
|---|---|---|---|
| Homepage | 一件工作的剖面 | 翻阅 / 追问 | 一件完整的"件"摆在桌上供你翻看 |
| Supply Chain | 时间轴里的当事方 | 跟随 / 拍板 / 改规矩 | 进入那家企业的 14 天 |
| Capability | 起草一次委托 | 配置 / 填写 | 回答"我们公司的什么事可以交给它" |

三页共享同一件核心组件——**工作对象**：首页展示它的剖面，供应链让它随时间流动，能力页把它作为待填的草稿。这是"同一世界"在代码层面的证据，而不靠共享配色。

**Homepage**：首屏不是 Hero + 定义，而是一件具体工作的完整记录（一条客户询盘或一次缺料，一件就够）。记录标题即页面 H1；"委托"这个词通过对象本身被学会，不靠解释段。

**Supply Chain**：页面是一个压缩了 14 天的工作台。时间是主导航；决策是真实操作，访客就是批准人。三个关键时刻：

1. **失效**（全页核心）：某天供应商交期变化，已批准方案的前提失败，工作**退回**访客面前——旧决定与新前提并排显示，访客必须重新决定；记录同时保留两次决定和它们之间的理由。这一个动作解释三件事（工作是持续的、前提被记着、权限边界存在），不需要任何解释文字。
2. **拆开**：一个开关，全场变暗，每个元素被标注 `[AutoMage 动作]` 或 `[企业设定]`（系统、角色、阈值、规则属于企业；收集、核对、追问、持有、追踪属于 AutoMage）。透镜本身就是论证。
3. **改规矩重放**：在设置里改一条边界（如"任何变化必须重新确认"→"±5% 预算内 AI 直接调整并报备"），重放同一段 14 天：这次事件没有回到你面前，只收到一张报备卡，审计里能看到 AI 动作和它的授权依据。自主边界这个概念不是被读到的，是被"被跳过或被打扰"的经历到的。

**Capability**：从访客自己的工作进入，三层展开：

1. 工作类型——用业务语言（对数、汇总、盯事、催办、成文、跑流程），不是 Skill 域；
2. 这项工作怎么被接手——委托模板：信息从哪来、AI 自主到哪、该问谁、交付什么、哪些 Skill 作为专业知识参与（Scenario→Capability→Skill 的三方关系在此展开）；
3. 完整 Skill 参考库——191 项保留检索、比较、来源状态，作为底层证据和技术/伙伴入口。

出口是一份讨论草稿："这件工作可能这样配置" + 参与的专业知识 + 待确认问题，带入联系页。

## 2. 每页最关键的一到两个动作

- **Homepage**：① **追问**——点任何结论看它是谁、何时、哪个系统说的；② **换视角**——同一件工作分别按决策者 / 参与者 / 设置者的眼睛看一遍。
- **Supply Chain**：① **推进时间**——拖动或步进 14 天；② **当责任人**——批准、退回、在失效后重新拍板、改设置重放。拆开透镜是第三动作，但只是十秒的开关。
- **Capability**：① **说出工作**——从列表选，或直接输入"一件我们常卡住的事"；② **配置**——回答三四个问题（数据在哪、谁负责、哪些环节希望它自己办）生成草稿。浏览 191 库是支线动作，不是主线。

十几秒即可完成的内容：首页的剖面（接了什么、AI 已做了什么、什么在等人、完成后给什么）。其余都应留给供应链（时间、规矩）或能力页（广度、配置）。

## 3. 信息层级与叙事进程

**Homepage**

1. 首屏：工作对象本体（演示标注常驻）。
2. 剖面追问：事实 / 未知 / 动作 / 等待的人。
3. 三种角色看同一件——系统经由熟悉的入口进入组织，不是新后台。
4. 两个门，各是一个具体问题："看一件真跑完的事"（供应链）/" 说一件你们的事"（能力）。不用卡片网格。
5. 底部：联系入口 + 一个收纳"边界与演示说明"的抽屉（现在散在三页的 FAQ 收敛到这里）。

**Supply Chain**

1. 顶部一行：真实 / 演示分界（企业背景真实；数据与执行为模拟）【假设：企业背景的具体程度待 owner 确认，未确认前按"场景重构"措辞】。
2. Day 0：预警进入 + 六角色追问链（复用现有 CompareSection 材料）——先让人感到"人肉搬运上下文"的重量。
3. Day 1–5：上下文、未知、方案、初次授权（现有 ScenarioWorkbench 扩展）。
4. Day 6：失效与退回（新，核心时刻）。
5. Day 7–14：重新决策 → 执行 → 回执 → 后续事件。
6. 拆开透镜。7. 改规矩重放（一对即可）。8. 一句桥接进 Capability："换一件事，还成立吗？"
9. 砍掉：InfoLoop 闭环、ValueCards、页内 Beta 表单、页内 FAQ、BringEvent（被桥接替代）。

**Capability**

1. 入口问句 + 可认出的工作 chips。
2. 工作类型 → 具体工作。
3. 委托模板（含自主边界与参与 Skill）。
4. 草稿箱（现有"咨询清单"rail 升级，机制沿用）。
5. 侧路：191 参考库（搜索、同类比较、来源状态）。
6. 联系携带草稿。直达到 Skill 详情的访客仍能看到"这项知识服务哪类工作"的父级提示（沿用 9/15 的层级修正）。

## 4. 三页如何共享世界而非模板

身份放在**文书语法**里，不放在全局主题里：

- 同一套对象本体与状态词汇：待确认 / 已授权 / 前提失效 / 已分派 / 已回执 / 已关闭 / 重新打开——`homepage-vnext.ts` 已定义大半，升为全站数据契约。
- 同一套标注系统：事实 / 推断 / 未知 / 演示 / 真实背景，同一个组件家族，出现在三页任何位置。
- 同一套引用交互：任何论断可点开看来源（谁、何时、哪个系统）。
- 色彩语义保留并修正一处：navy=人类权威、blue=AI 活动、green=已验证。前提修复：人类权威色不能还是深底上不可见的暗色。设计假设 H1：**暗桌面、亮纸张**——navy 是环境（桌子），工作对象是纸面，navy 作为纸上之墨（签字/授权）。系统的世界是暗的，人签署的文件是亮的。
- 动效规则：动效只表达工作在动（时间推进、状态变化、退回），取消常驻循环与粒子。

页面局部语言（故意不统一）：首页轻、静、疏；供应链密、多角色声部并发（IM 气泡作为证据材料，解除"禁气泡"禁令）；能力页参考式、表格密度、近无动效。

降级为局部选择的历史"全局规则"：全站连续暗画布（specs 02/03）、六节点循环图形与 loopRail→section 映射（01）、玻璃节点与粒子参数（04/06）、统一 Hero+英文 mono eyebrow+区段几何、"禁对话气泡"。

## 5. 复用与障碍

**直接复用**

- `src/lib/homepage-vnext.ts` 证据模型 → 全站数据契约。
- `ScenarioWorkbench.tsx` 状态机与无障碍/键盘/引导返回 → 供应链骨架，扩展而非重写。
- `CompareSection` 噪声碎片数据 → Day 0。
- Skill 目录管线（`skill-catalog.data.ts`、`skill-groups.ts`、保上下文分页、SkillDetail 的诚实字段）→ 能力页第三层。
- Beta/邀请码后端 + `/contact` → 草稿承接。
- Lenis/GSAP、reduced-motion 纪律、token 结构（换值留槽位）。

**会妨碍新体验**

- `InfoLoopSection`：圆形闭环直接宣称"生命周期是固定的"，与"可配置委托"相反——退役；其 inspector 面板的"点击看细节"并入工作对象。
- `SystemOverview` 输入→框→输出图 + 三段式：抽象定义，被剖面替代。
- `ValueCardsSection`：解释性文案，拆开透镜论证同一件事。
- 全站统一的"英文 mono eyebrow + 两行大标题 + 灰色侧注"骨架：同质化直接来源，废除默认地位。
- `--color-gate-human` 对 `--color-surface-command` 的对比度问题：语义倒置（人类权威不可见），先修。
- 191 条统一尾句 / 统一 gate 模板：参考库内容债，实施时逐条回原文落地。
- specs 01–06 作为全局硬约束：改按"某页局部手册"引用。

## 6. 整体体验方向

只有一个明显成立的，另两个是检查过并否决的：

- **主方向：工作对象的三种视图**（剖面 / 时间流 / 配置）。理由：它从产品定义直接长出来——产品承接持续推进的工作，解释它的网站自然应让访客翻阅、跟完、起草一件工作。三页姿态天然不同，同质化被结构性消解而非视觉修补。
- 否决一：**角色驱动**（老板/员工/管理员三条动线）。与"一人可兼多角"冲突；易唤起"老板监控"；角色切分不解释机制。保留其优点：角色视角作为首页第 3 拍的切换维度。
- 否决二：**编辑体刊物**。差异化强、利于对外介绍人传阅，但核心概念（边界、失效）只有交互能教，文字会退步回解释体。保留其优点：供应链案例产出一份可打印文本版作为辅助面。

## 7. 首个 vertical slice

**改造供应链页为 14 天世界**：Day 0 追问链 → 初次授权 → Day 6 失效退回 → 回执 → 拆开透镜 → 一组改规矩重放；桥接一句话。

选它不选首页的理由：

1. 复用率最高——状态机、素材、动效骨架已在，增量是时间轴、失效时刻、两个透镜；
2. 一次验证全站最脆的两个假设（H2：拆开/改规矩能以交互而非文案完成；H3：自主边界能被非技术负责人经验性地学到）；
3. 产出的工作对象组件，静态模式即首页首屏——**首页是第二片，不是独立新建**（H1：暗桌面亮纸张在该片验证）。

验证门（走现有 RCUT 流程与角色合同，新会话不给任何提示）：制造负责人跟完后能 (a) 说出 AutoMage 接走的是什么；(b) 在新情形下预测"这件事会不会回来找我"；(c) 拆开后区分企业设定与 AutoMage 动作。2/3 过 → 进首页片；不过 → 回炉本页机制。

实施提醒：进入编码前先读 `node_modules/next/dist/docs/` 中相关指南（本项目 Next.js 版本与训练知识不一致）。首页与其余页面在切片上线前保持现状。
